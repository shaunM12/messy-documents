# CONTEXT.md — Messy Document Search + Evaluation

This file is the source of truth for implementation. If code and this file disagree, this file wins.
Any change to locked decisions, schema, or dependencies must be made here first.

## 1. Goal
Build a small, testable retrieval system that:
1. Ingests messy documents of 3 types: plain text, table, messy layout.
2. Chunks each type with a type-appropriate strategy (NOT fixed-size for all).
3. Retrieves with hybrid search: BM25 + embeddings, fused with Reciprocal Rank Fusion (RRF).
4. Answers questions with cited sources, and says "I don't know" when evidence is weak.
5. Measures retrieval quality against a hand-built answer key (≥25 questions, dev/test split).
6. Supports delete/replace of document versions so stale chunks are never searchable.

## 2. Out of scope (binding)
- Multi-agent orchestration.
- Fine-tuning any model.
- A polished UI. A CLI is the only interface. Tests are the proof.
- MCP / plugin integrations.

## 3. Locked decisions
| # | Decision | Value |
|---|----------|-------|
| D1 | Old versions | **Hard delete.** Replacing a doc deletes all its old chunks in the same transaction as inserting new ones. No `is_current` flag. |
| D2 | Indexes | **Rebuilt from SQLite** on startup and after every ingest/delete. No incremental index patching. |
| D3 | Corpus | **Synthetic**, one fictional company ("Northwind Gear"), generated by `scripts/make_corpus.py`. Generated files are committed. |
| D4 | Answer step | **Extractive by default.** Optional LLM behind an `Answerer` interface; if used: `temperature=0`, fixed prompt in `answer.py`. Tests never require an LLM or network. |
| D5 | Eval split | Answer key ≥25 questions, tagged `split: dev` (~8) or `split: test` (~17). Thresholds tuned on dev only; README reports test. |
| D6 | Tooling | Python 3.11, `uv`, `ruff` (lint + format), `pytest`. |
| D7 | Config | All tunables live in `src/docsearch/config.py` only. No magic numbers elsewhere. |
| D8 | Token counting | Whitespace-split words (`len(text.split())`). No tokenizer dependency for chunking. |
| D9 | Chunk ID format | `{doc_id}:{version}:{slug(locator)}:{n}`; slug = lowercase, `[^a-z0-9]+` → `-`, strip `-`, max 40 chars; `n` = 0-based index within that locator. |
| D10 | Visibility rule | Chunk visible iff `"public" in chunk.visibility` OR `set(user_visibility) & set(chunk.visibility)`. CLI default user = `["public"]`. Filter BEFORE ranking. |
| D11 | Embedding model | `sentence-transformers/all-MiniLM-L6-v2`, normalized vectors. |
| D12 | Headline metric | **Hybrid Recall@5 on the test split.** |

## 6. Chunk schema (every field required)
```python
@dataclass(frozen=True)
class Chunk:
    chunk_id: str          # D9
    doc_id: str            # stable across versions, e.g. "policy_handbook"
    source_file: str       # "data/raw/policy_handbook_v2.md"
    doc_type: str          # "text" | "table" | "layout"
    locator: str           # section path, "page 2 block 3", "rows 10-19"
    text: str              # content indexed by BM25 and embeddings
    visibility: list[str]  # e.g. ["public"], ["customer:acme"], ["role:internal"]
    version: str           # "v1", "v2"
    updated_at: str        # ISO date "2026-10-01"
    metadata: dict         # type-specific extras (headers, columns, bbox)
```

## 7. Chunking strategy per type
**Plain text (markdown): structure-aware**
- Split on headings (`#`, `##`, `###`). One section = one chunk.
- Section > `TEXT_MAX_WORDS` (400) → split on paragraph boundaries with 1-sentence overlap.
- Prefix chunk text with heading path: `"Refunds > Digital goods: ..."`.
- Locator = heading path.

**Table (CSV): row groups with headers repeated**
- Never split a row. Group by `TABLE_ROWS_PER_CHUNK` (10) or by a key column when present (e.g. `plan`).
- Every chunk repeats the column headers; rows serialized as `col: value; col: value` lines.
- One extra "table summary" chunk: title, columns, row count.
- Locator = `"rows A-B"` or `"plan=Enterprise"`.

**Messy layout (PDF): layout-aware**
- Use pdfplumber word coordinates; detect columns by x-position clustering; read column-by-column.
- Strip header/footer lines that repeat on ≥50% of pages at similar y.
- Extract embedded tables and route them to the table chunker.
- Chunk by block (vertical gap > `LAYOUT_BLOCK_GAP`) within a page; never cross pages.
- Locator = `"page N block M"`; bbox in metadata.

## 8. Retrieval
- BM25 tokenizer: lowercase, strip punctuation, keep numbers and SKU-like tokens (e.g. `NW-1042`).
- Dense: cosine on normalized vectors.
- Each retriever returns top `CANDIDATES_N` (20) from **visible** chunks only (D10).
- RRF: `score(d) = Σ 1 / (RRF_K + rank_i(d))`, `RRF_K = 60`, ranks 1-based.
- API: `search(query, user_visibility, k=5, mode="hybrid"|"bm25"|"dense") -> list[ScoredChunk]`.

## 9. Answer step + "I don't know"
Return exactly `"I don't know"` with `abstained: true` if ANY:
1. No visible chunks returned.
2. Top dense cosine < `MIN_SIM` AND top BM25 score < `MIN_BM25` (both tuned on dev split).
3. Extractive mode: best sentence similarity to the question < `MIN_SENT_SIM`.
4. LLM mode: model outputs "I don't know", OR cites a chunk_id not in the provided context.

Output:
```json
{"answer": "...", "citations": [{"chunk_id": "...", "source_file": "...", "locator": "...", "version": "...", "updated_at": "..."}], "abstained": false}
```

## 10. Versioning (D1 + D2)
- `ingest(path, doc_id, version, visibility, updated_at)`: in ONE transaction delete all chunks with `doc_id`, insert new chunks; commit; rebuild indexes.
- `delete(doc_id)`: delete all chunks with `doc_id`; commit; rebuild indexes.
- Required test: ingest v1 → ask a question whose answer changed → ingest v2 → result cites v2 and no v1 chunk_id appears in any search mode.

## 11. Answer key (`data/eval/answer_key.jsonl`)
Write ONLY after chunking is stable (chunk IDs depend on it).
```json
{"qid": "q01", "split": "dev", "question": "What is the refund window for digital goods?",
 "relevant_chunk_ids": ["policy_handbook:v2:refunds-digital-goods:0"],
 "doc_type": "text", "answerable": true, "user_visibility": ["public"], "tags": ["paraphrase"]}
```
Required mix (≥25 total):
- ≥6 text, ≥6 table, ≥6 layout.
- ≥3 unanswerable (`answerable: false`, `relevant_chunk_ids: []`).
- ≥2 permission (answer exists but user can't see it → must abstain).
- ≥2 version (answer changed v1 → v2).
- Tags: `keyword` (SKUs, prices, IDs) and `paraphrase`, to compare BM25 vs dense.
- A question may list multiple relevant chunk IDs.

## 12. Metrics
Retrieval metrics use **answerable questions only**, k ∈ {1, 3, 5, 10}:
- **Recall@k** = |relevant ∩ top-k| / |relevant|
- **Precision@k** = |relevant ∩ top-k| / k
- **MRR** = mean of 1 / rank of first relevant hit (0 if none in top 10)

Answer metrics:
- **Abstention accuracy** on unanswerable + permission questions.
- **False abstention rate** on answerable questions.

Logging per run:
- `runs/{timestamp}_{mode}_{split}.jsonl`: per question (qid, retrieved ids, scores, ranks, hits, abstained).
- `runs/summary.csv`: one row per (run_id, mode, split, k, recall, precision, mrr).
- Always evaluate all three modes: bm25, dense, hybrid.

## 13. Tests (minimum)
- `test_chunk_schema`: all fields present and non-empty for every chunk type.
- `test_chunk_ids_deterministic`: re-chunking same input yields identical IDs.
- `test_text_chunker_respects_headings`
- `test_table_chunker_repeats_headers_and_no_split_rows`
- `test_layout_chunker_strips_headers_footers_and_keeps_column_order`
- `test_rrf_fusion` (hand-built rankings)
- `test_visibility_filter`
- `test_replace_removes_old_version` (all three modes)
- `test_delete_removes_from_both_indexes`
- `test_abstains_on_unanswerable_and_permission`
- `test_metrics` (toy ranking with known values)
- `test_answer_key_ids_exist`

No test may require network access or an LLM.

## 14. CLI


1. Project scaffold (`pyproject.toml`, `config.py`, `models.py`) + schema tests.
2. `scripts/make_corpus.py` + generated data.
3. Three loaders/chunkers + tests.
4. Store with ingest/replace/delete + tests.
5. BM25, dense, RRF with visibility filtering + tests.
6. Answer key (dev + test).
7. Eval + logging; run all 3 modes.
8. Answer step + abstention; tune thresholds on dev.
